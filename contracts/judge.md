# Judge verification

The judge's verification spec: how it gates an increment's behaviour. Read alongside build-judge-loop.md (the orchestration contract), which owns the roles, modes, profiles, flow, checkpoint and state, and points here for verification. The judge owns behaviour, not conventions or architecture (the reviewer owns those, see build-judge-loop.md, Roles): it type-checks first, runs the tests itself rather than trusting reports, proves a test fails when the code is wrong, and distinguishes a real failure from an environment block. The runners it drives honour the exit-code contract in agent-runner.md, so this spec is stack-neutral; only the commands underneath differ by stack.

## Test tiers
- Two tiers the judge runs and gates, no third judge tier. Among the tests the judge runs (the test path it drives through the agent test runner), a test's tier is decided by what it touches, not which feature or script it came from: no external dependency = unit test (fast, run-anywhere) wherever it lives; needs a live endpoint = integration test (slow).
- A project MAY declare a further tier the judge does NOT run: a separate-runtime tier outside the judge's test path (e.g. in TypeScript a front-end / browser-runtime tier of jsdom component tests). Gated by CI on the increment's PR, not by the judge, so it is not one of the judge's two tiers (the generator emits this CI; see docs/scripts.md and docs/templates/ts-react-mongo.md). The hollow-by-omission and misclassification rules below govern only the two tiers the judge runs; a CI-gated tier is a declared, separately-gated tier, not a gating test hidden from the judge behind a side command. Without a remote there is no PR and so no CI, so a project relying on this tier needs a remote to gate it.
- The project declares two test tiers, unit and integration, through commands the agent test runner drives (in the TypeScript stack the human verbose path is the npm scripts server:test:unit and server:test:integration). The judge does NOT hardcode test globs; tiers are driven through declared configs. Split mechanism (naming, directories) is the project's choice; the convention: name a test file after the module under test, beside it, with the tier as a suffix (e.g. in TypeScript a module crud.ts has crud.test.ts for unit and crud.integration.test.ts for integration). ONE file per module per tier, never two shared monolith files (those collide across branches and overwrite). Shared test helpers in one support module, imported not duplicated. (The reviewer checks tier classification: see build-judge-loop.md, Reviewer rules.)
- For repeated verification runs (each judge cycle) the judge invokes the project's agent test runner, .building/scripts/agent-tests.sh <tier>, placed under .building/scripts/ (gitignored, so loop machinery never enters the committed repo) and proved by the setup gate (which places and proves the hollow-check runner .building/scripts/agent-hollow.sh on the same footing; the hollow-test check's negative and restore-verify runs go through agent-hollow.sh, which drives this same runner internally, see Gates). It prints one terse summary line on pass and full output on failure, so a passing run costs a few tokens not the whole dump. It drives the same two tiers through the same configs as the human commands; only verbosity differs. The judge's pass REPORT still draws coverage, inventory and quality signals from full tooling (a single coverage run plus the project's type-check and lint); the terse runner is for repeated pass/fail verification, not a replacement for the report's measured data. The judge calls the runner as one bare command, relies on its terse line and exit code; it never appends shell (no `; echo` of exit status, no `| tail`), which would recreate a compound command and can truncate the full failure output the runner prints on purpose.
- Order: the judge runs the type-check FIRST, before any tests, the cheapest gate and nothing else type-checks (the tiers strip or do not check types; in TypeScript they run through esbuild and tsx, which strip them). It runs .building/scripts/agent-typecheck.sh; type errors are a rejection that consumes a judge attempt, a type-check config that cannot run is an environment block, not a rejection (see Type-check gate under Gates). If type-check is clean, run the unit tier; if unit fails, reject without running integration (units are cheap, fail fast). The runner's `both` mode enforces unit-then-integration order and short-circuit; the judge runs a single tier only for the negative runs, isolating one tier to prove a test fails when the code is wrong.
- After the unit tier, what the judge runs next per increment, and when the integration tier is verified, is the profile's call (build-loop-full.md per increment; build-loop-lite.md defers to the completion gate). The judge passes an increment only when the profile's per-increment gates pass. Tier definitions, the runner and the hollow-test here are shared by both profiles; only when integration runs differs.
- A tier with no tests, or that the project does not declare, is a vacuous pass ONLY where the increment genuinely has no behaviour for that tier. A tier that SHOULD have tests but selects zero is a hollow suite, a hard fail, re-checked every increment (setup proves selection once at the start, but a later increment can reintroduce a hollow tier through a misclassified test or config drift, so the judge re-checks the selected count each run, free since it already reads the count). Every test that gates an increment must be reachable through the declared tier configs the judge runs via .building/scripts/agent-tests.sh <tier>, the only surface the judge runs. The judge confirms each gating acceptance criterion is covered by a test it actually ran through .building/scripts/agent-tests.sh; a gating test reachable only behind a side command the judge never invokes leaves that criterion's main path untested through the declared tiers, a hollow tier by omission, a hard fail even when the tier selects other tests.
- The reviewer checks tier classification: a test with an external dependency MUST be in the integration tier, never unit, so unit stays dependency-free and run-anywhere. A gating test MUST be reachable through the declared tiers; a real gating test parked outside them, behind a side command the judge never invokes, is the same class of fault as a misclassified test, since tier is decided by what the test touches, not the feature or script it came from. Misclassification is a major.

## Integration endpoints
- Integration endpoints (e.g. a Mongo replica set) are an attended prerequisite the human provides, like gh auth. The loop does not start them.
- The project declares, in CLAUDE.md, for each endpoint: a readiness check and a bring-up command.
- Whenever the integration tier runs (per increment in full, at the completion gate in lite, see build-judge-loop.md, Build profile), the judge first checks declared readiness. If an endpoint is not ready, the judge does NOT run integration: it raises an ENVIRONMENT BLOCK, reports the project's bring-up command, waits for the human to bring it up and confirm, then re-checks and continues. An environment block is NOT a behaviour rejection and does NOT consume a judge attempt. It never emits a raw connection error as a verdict.
- The agent runner distinguishes a test failure (a tier ran and a test failed: a behaviour rejection that returns to the builder and consumes a judge attempt) from an environment failure (a tier could not run at all, e.g. broken/missing config, absent tooling: the runner exits 3). An exit-3 result is handled as an ENVIRONMENT BLOCK on the same terms as an unready endpoint: it does NOT consume a judge attempt and is never reported as a behaviour rejection. A broken environment is not the builder's defect.

## Gates the judge runs
These are the judge's behavioural gates. The orchestration-level gates (commit-only-on-green, conventional commits, scope guard, idempotent infra, blocked-halts-the-chain) live in build-judge-loop.md, Gates.
- Type-check gate: before the tiers, the judge runs the project's type-check runner as one named command, .building/scripts/agent-typecheck.sh, placed under .building/scripts/ (gitignored) by the setup gate, which places all three runners and proves each runnable. Verdict by exit code (contracts/agent-runner.md): 0 clean (proceed to the tiers); 1 type errors (a rejection, returned to the builder, consumes a judge attempt exactly like a failing test); 3 the check could not run (no config, the type-checker not installed, a config error), an environment block, not a rejection, consuming no attempt. The judge calls it as one bare command and relies on the exit code, never appends shell. The type-check is a gate, not merely a reported signal, because nothing else in the pipeline type-checks: the tiers strip or do not check types (in TypeScript, esbuild and tsx strip them), so a type error would otherwise reach a green pass.
- Hollow-test check: the judge proves a test fails when the code is wrong (negative run), run as one named command per check: .building/scripts/agent-hollow.sh <tier> <src-file> <test-file> <old-string> <new-string>. The judge supplies only the fault (an exact behavioural change that compiles, flip a value or comparison); the script owns the rest. It backs the file up under .building/ as a filesystem copy, which works on the UNTRACKED files a new increment adds where git checkout, git restore and git stash silently no-op and leave the break in the tree. It applies the fault, runs the tier scoped to this increment's own test file, classifies, restores from an exit trap whatever happens, then re-verifies green. Verdict by exit code: 0 the test caught the fault (asserts); 1 the tier stayed green so the test is HOLLOW (a major, increment fails); 2 the fault ran no tests so it was not behavioural (re-pick); 3 the file did not return to green after restore (halt). The check clears only on exit 0; a green negative run is the hollow failure, never a pass. The reviewer may suspect on read; the judge proves on run.
